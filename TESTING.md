# Testing Guide

This document covers testing patterns, conventions, and how to run the test suites for the Terraform State Manager frontend.

## Running Tests

All unit-test commands run from the `frontend/` directory.

```bash
# Run all unit tests once
npm test

# Run in watch mode (re-runs on file changes)
npm run test:watch

# Run with V8 coverage report
npm run test:coverage

# Run a single test file
npx vitest run src/services/api.test.ts

# Run tests matching a pattern
npx vitest run --reporter=verbose -t "X-CSRF-Token"
```

### Coverage

Coverage is generated by `@vitest/coverage-v8` and configured in `vitest.config.ts`. The thresholds are a **ratchet floor** — they only move up:

| Threshold  | Minimum |
| ---------- | ------- |
| Statements | 85%     |
| Branches   | 80%     |
| Functions  | 82%     |
| Lines      | 88%     |

These floors are enforced in CI: the unit-test job runs `npx vitest run --coverage`, which fails the build if any threshold is not met. They are set just under the suite's actuals and are stricter than the sibling registry frontend's 80/70/70/80. (The floors were recalibrated for the Vitest 3 → 4 bump, whose V8 coverage remapper reports different totals for the same all-green suite — see the comment in `vitest.config.ts`.)

Reports are written to `frontend/coverage/` in `text`, `text-summary`, `lcov`, and `json-summary` formats. CI uploads the `coverage/` directory as an artifact and, on pushes to `main`, derives the README coverage badge from `coverage/coverage-summary.json`.

### Coverage excludes

`vitest.config.ts` excludes test/spec files, `main.tsx`, `setupTests.ts`, `vite-env.d.ts`, and `*.d.ts` from coverage instrumentation. The included surface is `src/**/*.{ts,tsx}`.

## Unit Test Stack

| Tool                                                                                     | Purpose                                         |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------- |
| [Vitest](https://vitest.dev/) v4                                                         | Test runner (globals mode)                      |
| [happy-dom](https://github.com/capricorn86/happy-dom)                                     | DOM environment                                 |
| [@testing-library/react](https://testing-library.com/docs/react-testing-library/intro/)  | Component/hook rendering                        |
| [@testing-library/dom](https://testing-library.com/docs/dom-testing-library/intro/)      | Low-level queries                               |
| [@testing-library/jest-dom](https://github.com/testing-library/jest-dom)                 | Custom DOM matchers (`toBeInTheDocument`, etc.) |

The test environment is `happy-dom` (`vitest.config.ts`); `jsdom` is **not** used. The per-test timeout is raised to `15_000` ms (registry parity — heavy MUI dialog renders exceed the 5 s default on shared CI runners), and `__APP_VERSION__` is defined as `'0.0.0-test'`.

### Setup file (`src/setupTests.ts`)

The setup file:

1. Registers `@testing-library/jest-dom/vitest` matchers.
2. Imports `./i18n` so `useTranslation()` returns English strings in every test (prevents react-i18next from suspending the render).
3. Installs a spec-compliant in-memory `localStorage` on `globalThis` — Node ships a built-in `globalThis.localStorage` whose API diverges from the Web Storage spec, so it is replaced to keep storage-dependent code (theme, help panel, nav groups, i18n) deterministic.

## Unit Test Patterns

### Spying on the shared Axios instance

`services/api.ts` exports a shared `apiClient` instance plus a flat `api` map of thin wrappers. Tests **spy on the instance** rather than mocking the whole `axios` module, then assert the `(method, url, body, config)` tuple per call:

```ts
import { api, apiClient, readCookie } from './api'

beforeEach(() => {
  get = vi.spyOn(apiClient, 'get')
  post = vi.spyOn(apiClient, 'post')
  // ...
})

afterEach(() => {
  vi.restoreAllMocks()
  document.cookie = 'tsm_csrf=; expires=Thu, 01 Jan 1970 00:00:00 GMT'
})
```

### Testing the interceptors directly

The interceptor callbacks are reachable on the instance via its internal `handlers` array, so the CSRF request interceptor and the 401 response interceptor are exercised without a network round-trip:

```ts
it('attaches X-CSRF-Token on mutating requests when the cookie is set', () => {
  document.cookie = 'tsm_csrf=token-1'
  for (const method of ['post', 'put', 'patch', 'delete']) {
    const out = requestHandlers()[0].fulfilled({ method, headers: {} })
    expect(out.headers?.['X-CSRF-Token']).toBe('token-1')
  }
})
```

`api.test.ts` also covers `readCookie` (name lookup, URI decoding, absence) and the 401 handler clearing auth storage. `api_redirects.test.ts` covers the full-page redirect helpers (`login`, `logout`).

### Testing context providers

Context tests render a consumer inside the real provider and capture the context value via a callback, then drive it with `act`/`waitFor`. `AuthContext.test.tsx` exercises the OIDC/dev/LDAP login paths, logout, `refreshSession`, `hasScope` (including the `admin` wildcard), and the session-expiry warning timer (with fake timers). It mocks `services/api` at the module level for the endpoint calls.

### Testing components with routing and auth

Components that depend on the router are wrapped in `MemoryRouter`. Components that read `useAuth()` mock the context module rather than wrapping a real provider:

```ts
vi.mock('../contexts/AuthContext', () => ({ useAuth: () => mockUseAuth() }))
mockUseAuth.mockReturnValue({ isAuthenticated: true, isLoading: false, hasScope: () => true })
```

`ProtectedRoute.test.tsx` covers the loading spinner, the unauthenticated redirect, and the insufficient-scope message.

## Unit Test Inventory

The suite contains **~57 Vitest spec files** (count with `Get-ChildItem frontend/src -Recurse -Include *.test.ts,*.test.tsx | Measure-Object`). They sit as siblings of the code they cover, organized by domain under `frontend/src/`:

| Directory                         | Coverage focus                                                                                                                            |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `src/` (root)                     | `App`, `i18n`, `navigation`, `theme`                                                                                                      |
| `services/`                       | API client wrappers + CSRF/401 interceptors (`api`, `api_redirects`), `errorReporting`, `queryKeys` stability, `setupApi`                 |
| `contexts/`                       | `AuthContext`, `ThemeContext`, `HelpContext`, `AnnouncerContext`                                                                          |
| `hooks/`                          | `useRouteFocus` (route-change focus + announcements)                                                                                      |
| `components/`                     | ~16 component specs — Layout, ProtectedRoute, ErrorBoundary, CommandPalette-adjacent dialogs, About modal, drift/section panels, breadcrumbs, session-expiry warning, suite switcher, skeletons |
| `pages/`                          | Public/feature pages — Dashboard, Sources, Drift, Version Lab, Schedules, Reports, Transfer, Login, Callback, Setup Wizard, API docs, plus `coverage_gapfill*` top-ups |
| `pages/admin/`                    | Every admin page — Admin Dashboard, Users, Organizations, Roles, Group Mappings (OIDC), mTLS, SSO, Notifications, Audit Log, API Keys     |
| `utils/`                          | `authStorage`, `scopes`                                                                                                                   |

> The directory layout is the source of truth — code added under `frontend/src/` should ship with a sibling `*.test.ts(x)`. The ratchet coverage gate (85/80/82/88) is the mechanism that enforces it: an untested file pulls the totals below the floor and fails CI.

## E2E Tests

### Stack

E2E tests use [Playwright](https://playwright.dev/) and live in their own package under [`e2e/`](e2e/) (separate `package.json`). They are a **thin smoke pack run against the live Docker Compose stack**, deliberately **not PR-gated** — run them on demand and before UAT/releases.

Configuration: `e2e/playwright.config.ts`

| Setting     | Value                                                                  |
| ----------- | --------------------------------------------------------------------- |
| Base URL    | `http://localhost:3001` (override with `TSM_E2E_BASE_URL`)             |
| Browser     | Chromium only (`Desktop Chrome`)                                       |
| Workers     | `1` (tests share one live backend, so they run serially)              |
| Retries     | `0`                                                                    |
| Timeout     | 60 s per test, 10 s per `expect`                                       |
| Trace       | `retain-on-failure`                                                    |
| Screenshot  | `only-on-failure`                                                      |
| Reporter    | `list`                                                                 |

### E2E test files

```text
e2e/
  fixtures/
    auth.ts            # loggedInPage fixture (dev-login cookie) + csrfToken helper
  tests/
    pages.spec.ts      # every page renders with real data from the live stack
    flows.spec.ts      # one critical flow per pillar (browse state, drift lifecycle, API-key lifecycle)
```

`pages.spec.ts` proves each route renders against real backend data (the FE/BE contract drift that unit tests miss). `flows.spec.ts` runs end-to-end flows through the real stack: browsing a state's analysis/outputs/history tabs; the drift record lifecycle (ingest → acknowledge in the UI → resolve, self-cleaning); and the API-key lifecycle (create in the UI → authenticate a cookieless request with the `tsm_`-prefixed secret → delete and confirm revocation).

### Running E2E tests locally

1. Start the dev Compose stack (PostgreSQL, backend, frontend, Keycloak):

   ```bash
   cd deployments
   docker compose up -d
   ```

   The frontend is served on `http://localhost:3001` and proxies `/api` to the backend. The backend must run with `DEV_MODE` enabled (the dev stack does) so the dev-login fixture works.

2. Install Playwright and run the smoke pack:

   ```bash
   cd e2e
   npm install && npx playwright install chromium
   npx playwright test
   ```

### Authentication in E2E tests (`fixtures/auth.ts`)

The `loggedInPage` fixture establishes a cookie session by POSTing to `/api/v1/dev/login` (which sets the HttpOnly auth cookie). Because `page.request` shares the page's cookie jar, subsequent API calls are authenticated automatically. The `csrfToken(page)` helper reads the `tsm_csrf` cookie so test helpers can perform mutations:

```ts
import { test, expect, csrfToken } from '../fixtures/auth'

test('drift record lifecycle', async ({ loggedInPage: page }) => {
  const csrf = await csrfToken(page)
  await page.request.post('/api/v1/drift/ingest', {
    headers: { 'X-CSRF-Token': csrf },
    data: { /* ... */ },
  })
  // ...
})
```

Tests are **self-cleaning** — each sweeps its own leftovers (e.g. API keys prefixed `e2e-smoke`, drift records keyed `e2e-smoke.tfstate`) so reruns against the same live store stay green.

### Adding a new E2E test

1. Add a test to `e2e/tests/pages.spec.ts` (render check) or `e2e/tests/flows.spec.ts` (end-to-end flow).
2. Import `test`/`expect` from `../fixtures/auth`; use `loggedInPage` for authenticated cases and `csrfToken(page)` for mutating API calls.
3. Prefer role-based locators (`getByRole`, `getByText`) for resilience.
4. Keep tests self-cleaning and independent — set up and tear down your own state.

## CI Integration

The frontend CI lives in `.github/workflows/ci.yml` and runs on every PR and on pushes to `main`. The required jobs are:

- **Lint** — `npm run lint` (ESLint, `--max-warnings 0`).
- **Typecheck** — `npx tsc --noEmit`.
- **Unit Tests** — `npx vitest run --coverage` (ratchet gate); uploads `frontend/coverage/` as an artifact and, on pushes to `main`, updates the coverage badge gist.
- **Build** — `npm run build` (`tsc && vite build`); uploads `frontend/dist`.

The Playwright smoke pack is **not** part of this gating workflow — it runs on demand and before UAT/releases against the live Compose stack.
